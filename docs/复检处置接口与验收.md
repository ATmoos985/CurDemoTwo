# 复检处置接口与验收

本批在现有业务接口上实现产出复检，独立计算作业及 `/api/v2` 仍按总体方案后续建设。

## 业务口径

- 实物身份为 `planId + pieceId`，只允许处置已确认报工的已切裁片（原 `QUALIFIED` 或 `REJECTED`）。未切、已撤回、缺少逐件明细的历史记录不能自动处置。
- 一次请求处置一件，目标为 `REMNANT`（转料头）或 `SCRAP`（报废）。本期每件仅允许一次处置，不支持撤销处置、再次分类或多块回收。
- 原始报工数量、逐件结果、面积及原材料耗用保留；原良品处置后净完成量减一，原异常件处置不再次减良品。
- 回收矩形必须完全位于已经变换后的裁片局部轮廓中，满足原方案最小回收宽、长；包含凹口的外接框不能入库。坐标单位 mm，禁止 NaN、无穷值和越界。
- `RECOVERABLE` 表示检验人确认该回收区域可用，生成 AVAILABLE 库存；`QUARANTINED` 为待检隔离，不能扫码选料或用于排料。本期不提供隔离放行接口。
- 全件面积扣除回收矩形面积后的部分为本次报废面积。当前净损耗 = 原损耗 + 被撤销良品面积 − 新回收面积（原异常件本来已记入原损耗）。
- 有复检记录的原报工禁止整单撤回，演示重置也不得删除这条材料追溯链。补产仍按任务剩余需求重新选料、排料、报工。

## 调用

`GET /api/cutting/reports/{planId}/quality-dispositions`

返回原报工及当前只读投影：

| 字段 | 含义 |
| --- | --- |
| `qualityRevision` | 当前处置记录数，首次为 0 |
| `qualityDispositions` | 有独立 ID 的追加式处置记录 |
| `netFinishedPieceCount` | 当前净良品件数 |
| `netPieceArea` / `netRemArea` / `netWasteArea` | 当前良品、回收、损耗面积，m² |
| `netUtilization` | 当前良品面积 ÷ 原实际耗用面积 × 100，单位 %，与原 utilization 一致 |

这些新增字段也用于任务报工列表、方案详情和报工返回；旧字段保持原始语义。

`POST /api/cutting/reports/{planId}/quality-dispositions`

```json
{
  "operationId": "8c87e901-7468-4811-ab5e-7d43a790908b",
  "expectedRevision": 0,
  "pieceId": 1,
  "disposition": "REMNANT",
  "reason": "复检发现右侧破损，实测左上区域可回收",
  "inspector": "检验员甲",
  "recovery": {
    "x": 0,
    "y": 0,
    "width": 500,
    "length": 500,
    "location": "隔离区 B-01",
    "quality": "QUARANTINED"
  }
}
```

报废时 `disposition` 填 `SCRAP`、`recovery` 明确填 `null`。所有命令字段均需提供，整数编号/版本不接受小数、字符串或 null，拒绝未知字段、拼接 JSON。检验人 1–80 字，原因 1–500 字，库位 1–100 字，均不能为空白。

成功 HTTP 200，返回处置记录：`id`、`planId`、原始 `command`、`demandId`、`originalOutcome`、`pieceAreaMm2`、`recoveredAreaMm2`、`scrapAreaMm2`、`remnantId`、服务端 `createdAt`。此记录内面积为 mm²，由字段名明确区分报工投影的 m²。

`operationId` 是报工范围内的幂等键，16–80 个字母、数字、下划线或连字符，建议 UUID。完全相同的命令重试返回原记录；同一键更换任何内容、裁片已经处置、版本过期或数据库写入竞争返回 HTTP 409。输入或业务校验错误返回 HTTP 400，正文含 `message`。

前端遇到响应丢失会锁定原命令，允许重试同一次处置；不会重新生成操作编号。409 要关闭窗口刷新记录再操作；400 可修正输入。成功后刷新任务及库存，原记录不被覆盖。

`GET /api/remnants?includeQuarantined=true` 是现有料头列表的可选扩展，返回可用及隔离库存；省略参数仍仅返回可选库存。料头新增可空来源字段 `sourceReportId`、`sourcePieceId`、`qualityDispositionId`，兼容旧快照。

## 模块和事务

- HTTP：`FabricCutController` 负责严格解码及 400 / 409 映射。
- 业务：`QualityDispositionRules` 只做资格与几何校验；`RemnantService.disposeQuality` 在现有事务边界内追加事件并生成库存；完成量和当前指标按原记录加事件投影。
- 算法：复用既有轮廓面积与包含验证，不修改求解策略，不由算法写库存。
- 前端：`business/cutting/quality-review.js` 管理表单与重试；入口位于报工记录内。业务展示适配当前结果，通用画布不调用质量接口。
- 存储：事件暂存于原报工聚合的 `qualityDispositions` 列表，JSON 文件和 JDBC `cut_report.data_json` 都可持久化；不改原报工事实字段。JDBC 用既有版本 CAS 和数据库事务，库存与事件一起提交；失败恢复整份快照。
- 文件存储仍限单进程；多实例使用 JDBC。本批未把事件独立迁移为质量流水表，未完成外部 WMS 对账。
- `inspector` 目前是调用者填写的姓名，不能当作已认证身份；权限、签名审计、租户隔离及 AI/MCP 授权属于后续阶段。

## 验收入口

Java：`QualityDispositionTests`、`QualityDispositionRulesTests`、`JdbcInventoryTests`；JavaScript：`quality-review.test.mjs`、面积口径和打印测试；真实浏览器：`src/test/browser/quality-review.cjs`，必须指定非 8080 的隔离测试服务。

验收覆盖：10 件变 8 件、原卷耗用不变；转料头与报废；已判异常不重复扣良品；凹多边形几何；隔离不可选；失败回滚；数据库并发与重启幂等；严格输入；已提交但响应丢失后的重试；打印和库存追溯；1366×768、1920×1080 窗口布局。
