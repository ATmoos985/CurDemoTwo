## 二、Iteration 2 并发/幂等/双存储一致性/避疵边距/前端状态修复记录

1. **草案确认与作废按 `draftId` 互斥防半一致（`WorkbenchDraftService.java`）**：
   - 引入基于 `ConcurrentHashMap<String, DraftLockEntry>` 引用计数的按 `draftId` 粒度局部 `ReentrantLock`（`withDraftLock`），串行化同一草案的 `confirmDraft`、`discardDraft` 与 `confirmSchemeWithDraft`。
   - `confirmSchemeWithDraft` 在锁内读取草案并记录 `checkInstant` 作为预检与后续 `transitionFromPending` 的时钟基准，彻底消除“已调用 `studioService.confirmScheme` 扣减需求并锁料，却因并发 `discardDraft`、不同 `idempotencyKey` 并发确认或跨过 `expiresAt` 而抛 409”的账实撕裂风险，且严格保持 `business.cutting` 对 `business.workbench` 零反向依赖。
2. **多料批量草案 `Idempotency-Key` 幂等重放与异参冲突校验（`MultiMaterialDraftOrchestrationService.java`）**：
   - 传入非空 `idempotencyKey` 时，对规范化请求体计算 SHA-256 指纹（`requestFingerprint`），由 `idempotencyKey` 确定性派生 `batchGroupId`（`MMB-<sha256前12位>`）与各段 `clientRequestId`（`<batchGroupId>-<seq>-<fingerprint前16位>`），并按 `idempotencyKey` 互斥串行。
   - 编排前先查询 `batchGroupId` 存量草案：同键同参直接幂等返回原批次（相同 `batchGroupId`、`draftIds`、`resultIds`，零重复写入，支持冷重启持久化验证）；同键异参直接抛出 `409 IDEMPOTENCY_CONFLICT`。
3. **`JdbcWorkbenchDraftStore` 与 `FileWorkbenchDraftStore` 清理及排序等价性修复**：
   - `JdbcWorkbenchDraftStore.expireAndPurge` 标态为 `EXPIRED` 时保留 `updated_at = expires_at`，并在 `DELETE` 语句按状态精确取终态基准时间（`CASE WHEN status='EXPIRED' THEN COALESCE(expires_at, updated_at, issued_at) ...`），实现与 `FileWorkbenchDraftStore` 首轮物理清除过期超保留期草案完全等价。
   - `FileWorkbenchDraftStore.listByTask` 统一改用 `parseEpochMillis` 比较时间序。
4. **料头 `REMNANT` 归档保留 `Defect.margin`（`MultiMaterialDraftOrchestrationService.java`）**：
   - `archiveSegment` 归档排布时通过 `DefectWindowSupport.sliceForWindow` 将 `REMNANT` 原始 `Defect.margin` 外扩至 `Exclusion` 禁区，并保留 `severity` 与 `avoidancePolicy`，与 `WorkbenchPlanOrchestrator` / `GlobalPlanningService` 避疵口径一致。
5. **前端收件箱单发请求、乱序丢弃与草案实时阻断同步（`useDraftInbox.ts`、`draftInboxApi.ts`、`CuttingWorkbenchPage.tsx`、`ExternalPlanBanner.tsx`、`DraftInboxDrawer.tsx`、`useWorkbenchSolver.ts`、`api-request.js`）**：
   - `useDraftInbox` 使用 `statusFilterRef` / `batchGroupFilterRef` 消除与 `useEffect` 的双重请求触发，引入递增 `requestSeqRef` 与 `AbortController` 丢弃所有慢响应乱序旧数据与取消信号。
   - `DraftInboxDrawer` 在 `drafts.length < total` 时新增已展示条数提示与「加载更多」增量分页按钮。
   - `CuttingWorkbenchPage` 接入 `onActiveDraftSynced`、`onDraftConfirmFailed`、定时到期刷新与本机草稿恢复状态同步，并通过 `evaluateActiveDraftBlockedReason` 与 `ExternalPlanBanner` 动态校验 `expiresAt < nowMs`（不仅依赖静态 `expired` 字段）。
6. **补充回归测试**：
   - 后端 `WorkbenchOrchestrationTests` 新增 4 项用例（`CountDownLatch` 延迟+HTTP 并发对抗 `confirm`/`discard` 与异键并发确认、多料 `Idempotency-Key` 幂等重放与异参 409 及冷重启、双存储 `expireAndPurge` 首轮即删与 ISO 排序一致性、料头 `Defect.margin` 外扩保留），共计 14/14 通过。
   - 前端新增 `frontend/src/pages/workbench/__tests__/useDraftInbox.test.ts`（4 项用例：单发请求防双发、慢响应乱序丢弃与 AbortSignal、活动草案同步与加载更多、`evaluateActiveDraftBlockedReason` 动态过期阻断），Vitest 共 20 文件 103/103 通过。

## 三、Iteration 3 边界竞态与冷重放收尾修复记录

1. **临界过期场景下确认落库与滚动清理按 `draftId` 互斥防半一致（`WorkbenchDraftStore.java`、`JdbcWorkbenchDraftStore.java`、`FileWorkbenchDraftStore.java`、`WorkbenchDraftService.java`）**：
   - 在 `WorkbenchDraftStore` 新增 `listCleanupCandidateIds(long nowMs, long purgeBeforeMs)` 与 `expireOrPurgeSingle(String draftId, long nowMs, long purgeBeforeMs)`（保留 `expireAndPurge` 向后兼容），并在 JDBC 与 File 双存储实现等价的先过期标态再按终态时间戳物理清除逻辑。
   - `WorkbenchDraftService.cleanupExpiredDrafts(long customRetentionHours)` 改为先检索候选 ID 再逐条通过 `tryWithDraftLock` 获取按 `draftId` 粒度锁（若当前正在被跨线程确认/作废或同线程外层已持锁，立即跳过本条），彻底消除“预检通过后落库跨越 `expiresAt` 期间被清理线程将草案改标为 `EXPIRED` 甚至物理删除，从而抛出 `409 DRAFT_EXPIRED` 但正式方案与锁料已落库”的撕裂风险。
2. **修复 `useDraftInbox` 非静默刷新被静默刷新打断后 `loading` 永久卡死（`frontend/src/pages/workbench/useDraftInbox.ts`）**：
   - 在 `refreshDraftInbox` 的 `finally` 中，只要 `seq === requestSeqRef.current`（当前已无更新请求接管），无论本次请求是否 `silent`，统一复位 `loadingRef.current = false; setLoading(false);`，恢复抽屉展示与 `loadMoreDrafts()` 增量分页。
3. **消除 `MultiMaterialDraftOrchestrationService` 冷重启幂等重放对实时规划的耦合（`MultiMaterialDraftOrchestrationService.java`、`MultiMaterialReplaySupport.java`）**：
   - 当 `idempotencyCache` 未命中（冷重启或缓存淘汰）但命中持久化 `existingDrafts` 且请求指纹校验通过时，不再重跑 `globalPlanningService.planMultiMaterial(planReq)`，改为通过独立同包无环工具类 `MultiMaterialReplaySupport.rebuildPlanResultFromArchived(...)` 直接从持久化草案与已归档的 `StoredOptimizationJob`（`optimizationService.findJobWithSource`）确定性重建 `MultiMaterialPlanResult`（`remnantAllocations`、`rollOptions`、放置快照与件数/面积统计），彻底与后续任务消耗及实时库存解耦。
4. **补充 Iteration 3 回归测试**：
   - `WorkbenchOrchestrationTests` 新增 `confirmSchemeWithDraftBoundaryExpiryConcurrentCleanupDoesNotSplitState`（JDBC+File 双存储、跨越 `expiresAt` 并发与同步重入清理验证草案正确进入 `CONFIRMED`）并强化 `multiMaterialDraftsIdempotencyKeyReplayAndConflictWork`（消耗清零任务需求 + 拒绝调用 `planMultiMaterial` 的冷重启重放校验），共计 15/15 通过。
   - `frontend/src/pages/workbench/__tests__/useDraftInbox.test.ts` 新增“非静默刷新被静默刷新打断后 `loading` 复位与 `loadMoreDrafts` 正常发起第 2 页”回归测试，共 5/5 通过（Vitest 20 文件 104/104 通过）。
