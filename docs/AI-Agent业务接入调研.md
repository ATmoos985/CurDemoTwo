# AI Agent 如何帮排程员比较排料方案

调研基线为 2026-11-26 已发布的 `master` 提交 `3d1747d`。本文是 `AI-agent` 分支的实施建议。首版使用者和任务已确定为排程员在现有工作台比较方案，先从二维裁切开始。

## 排程员实际会用它做什么

排程员在工单里选中两份排料结果，问“这单必须齐套，A 和 B 哪个更省布？”。助手首先核实两份结果属于当前工单、用户有权查看，再调用后端比较。工作台并排显示需求件数、已排件数、缺件、占用长度、利用率及其分母，列出影响结论的约束差异，并提供两张排料图的入口。所有数字来自已保存的结果或有明确口径的业务字段，模型只组织解释。

例如，A 更短但少排两片，B 全部排入，助手应说明 B 满足本单齐套要求，同时指出 A 少排的两片。若换了母卷、疵点窗口或裁片间距，则列出各方案的可行性和变化条件。只有后端判定可比的指标才能计算节省量。排程员仍可选择另一方案，并在原工作台办理确认。此例仅说明验收行为。

### 首版要解决的三个具体问题

1. **弄清正在比较哪一张图。** 手调候选可以继承原结果号，同时改变裁片位置。后续几何校验会更新工作台状态，但不会为这次编辑生成新的归档结果。首版只接入可校验为原始归档版本的候选。手调版本应提示重新生成可存档的结果，或由后续版本为编辑后的图单独归档。求解请求中的材料标识也可能只是由画布宽长生成。应用层应绑定工单、实物卷或料头、窗口起点、材料及布局版本。两张等宽画布可能来自不同的卷。[手调结果](../frontend/src/pages/workbench/useWorkbenchBoardEdit.ts#L250) · [校验流程](../frontend/src/pages/workbench/useWorkbenchBoardEdit.ts#L672) · [画布材料标识](../frontend/src/lib/domain/nesting-request-adapter.js#L371)
2. **把“齐套”和“利用率”算清楚。** 后端分别提供加工区域利用率、齐套版面利用率和含补空片的版面利用率。工作台候选卡会把补空裁片面积计入自己的百分比。表格应按同一个指标标识展示分子、分母及单位。默认 MCP 摘要省去了履约明细，需由后端从两份归档的 `layout.fulfillment` 逐规格提取应排、已排和缺口，补空备用片单列。要求齐套时核对每项缺口及齐套状态，仅凭作业成功或满足原请求的标志不足以判断。[后端指标定义](../src/main/java/com/example/cutdemotwo/business/optimization/OptimizationService.java#L991) · [工作台利用率](../frontend/src/pages/workbench/useWorkbenchSolver.ts#L516) · [逐项履约](../src/main/java/com/example/cutdemotwo/contracts/nesting/NestingResult.java#L29) · [MCP 结果摘要](../integrations/mcp/src/server.mjs#L225)
3. **给“省多少布”一个可验证的单位。** 现有二维比较服务给出已登记面积指标的差值。占用长度单独存在可空的 `marker.occupiedLengthMm` 中，工作台还可能据图形推算长度。首版只有在两案都齐套、材料与工艺条件一致且两侧有同口径占长时，才由后端计算预计节省的毫米数。其余情况可显示两侧有来源的原值并说明差异，缺失项标为“未提供”。[面积与占长取值](../src/main/java/com/example/cutdemotwo/business/optimization/OptimizationService.java#L998) · [工作台占长取值](../frontend/src/pages/workbench/useWorkbenchSolver.ts#L515)

## 分支上的实施顺序

1. **先交付“解释已选方案”。** 在工作台候选列表增加“比较所选方案”。后端通过登录会话验证工单与两个结果的关联，在应用层调用现有比较服务，生成包括结果号、齐套情况、指标来源和不可比原因的结构化结果。固定表格由前端直接展示，模型根据同一份数据回答追问。模型超时仍可读表、看图。先实现这一个端到端用例。
2. **再交付“替我跑两种策略”。** 将当前前端组装工艺输入的规则收敛到工作台和 Agent 共用的服务端适配层，以现有二维请求做一致性测试。冻结同一时点的任务余量、材料版本、可裁窗口、疵点、方向、间距和单位，仅在允许范围内改变策略。为两次请求分配独立幂等键，分别记录输入哈希、作业号和结果号。同一策略重试时沿用原请求和键，刷新后恢复原作业。先核对可比性，再给结论。[工作台输入适配入口](../frontend/src/pages/workbench/useWorkbenchSolver.ts#L459) · [Microsoft 异步请求模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply)
3. **有采用需求后再接“提交待确认方案”。** 增加持久化建议，绑定创建人、工单、结果号、输入哈希、业务版本、有效期和预期影响。排程员看到这些信息后点击确认，由后端在同一业务事务内复核授权、版本和幂等条件，再调用已有确认用例。过期或库存变化时返回变更原因并要求重算。预占、派工、报工及复检保留各自原有入口。

模型接入放在后端，通过一个可替换的模型接口调用。第一次运行只传当前问题和已授权的指标摘要，原始 DXF、裁片轮廓、客户备注及访问凭据留在业务系统。试点使用脱敏案例。生产模型选型取决于图纸和订单数据能否外发，可用获准的托管模型或内网推理服务。模型密钥、调用上限、超时和费用预算由服务端管理。记录每次比较的操作者、工单、两个结果号、工具状态、耗时和用量，便于回答“当时为什么推荐这个方案”。几何放置仍由现有求解器完成。

## 怎样判断值得推广

本次在分支基线上执行 MCP 适配器测试 12 项，成功 12、失败 0、跳过 0。另用隔离 Spring 服务和独立数据目录通过 stdio 实测 11 个检查点，执行 11、成功 11、失败 0、跳过 0。覆盖同键重试、取回输入与结果、同一结果与自身比较差值为零，以及试算前后库存对账快照一致。尚需单独验证两个不同方案的业务解释、生产用户授权和排程员的实际选择。[隔离服务验收脚本](../integrations/mcp/test/live-smoke.mjs)

建议从 20 个脱敏或合成工单开始，每例重复 3 次。样本覆盖两案都齐套、一案缺件、总件数相同但缺不同规格、补空备用片、约束或指标口径不同、工具超时和越权读取。第二、三阶段再加入计算重试和库存版本变化。由保存的输入、求解结果、权限判定和库存流水确定参考答案，允许“并列”“两者都不满足”和“条件不同，无法判优”。[Anthropic 工具评测实践](https://www.anthropic.com/research/writing-tools-for-agents)

让排程员交叉使用现有工作台、新对比表、新对比表加 AI 解释，轮换工单与顺序。统一从打开候选计时到作出判断，分别看表格和模型各自节省多少时间。记录错选率、采纳率、每次有效比较的费用和新增求解次数。

建议放行门槛为关键错误零次，包括跨权限返回数据、试算产生库存流水、将缺件说成齐套，以及对不可比指标声称节省。其余事实问答正确率至少 90%。目标是相对现有工作台，中位判断用时降低 30%，错选率不升高。若单用对比表已达到目标，而模型没有额外改善时间或正确率，优先推广对比表。以上数字均为试点建议，尚无模型或排程员实测结果。
