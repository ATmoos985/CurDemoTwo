# 统一计算作业接口与验收

本文件对应第三批的第一阶段（03a）：独立于库存业务的单实例异步计算服务。外部系统可以提交完整问题快照、轮询计算、读取输入与结果、取消和幂等重试。数据库作业表、租约、分布式 worker、SSE、一维、多材料分配、方案比较和 MCP 尚未接入，不计入本阶段完成范围。

## 1. 边界与契约

- `/api/v2` 是作业服务协议；当前几何载荷复用已经验证的 `nesting-v1` 契约。外层 `schemaVersion=2.0`，`problemType=NESTING_2D`，内层 `problem.schemaVersion=1`。总体设计 §6.2 的多材料/字符串需求 ID 示例仍是未来目标，不可直接发送本接口。
- 此阶段有意复用已有单材料契约与引擎校验，避免另写一套几何规则。未来新增问题类型以独立 profile 接入，不静默丢掉多材料、seed、刀缝或未知约束。
- 新增 `contracts/jobs` 负责公共作业 DTO；`business/optimization` 负责调度、状态、幂等与结果封装；`persistence/OptimizationJobStore` 负责独立归档。算法层不依赖这些上层模块。
- `SolverFactory` 提取共用输入校验和引擎选择，增加每次调用的 `allowFallback` 参数；原 `solve(problem)` 和 v1 HTTP 接口保持原降级策略。
- 标准输入使用 mm，输出面积 mm²，坐标为材料局部左上原点。材料 ID 是调用方快照标识，不要求在内部库存存在。
- 所有作业都不创建业务任务/方案/报工，不预约、不扣原料、不生成实际料头。输出余料是计算候选区域。

可直接读取：

- OpenAPI 3.1：`/api-v2/openapi.json`
- JSON Schema 2020-12：`/api-v2/optimization-request.schema.json`
- 可运行请求：`/api-v2/example-request.json`

JSON Schema 描述字段结构，实际还需通过引擎能力、工艺、精度、数量、轮廓和结果校验。未知字段、重复 JSON 字段、尾随 JSON、小数转整数及字符串转数值均被拒绝。内层沿用 v1 默认：空数组、未指定的数值约束为零、布尔约束为 false、pieceGap 为零、engine 缺失为 auto；外层降级和齐套选项必须明确填写。

## 2. 接口

| 接口 | 行为 |
| --- | --- |
| `GET /api/v2/capabilities` | 返回引擎实际可用性、工艺/几何/目标/精度、当前限额和已实现功能 |
| `POST /api/v2/problem-validations` | 校验问题与引擎适用性；不执行求解，也不保存作业 |
| `POST /api/v2/optimization-jobs` | 先归档再入队，返回 HTTP 202、作业及 Location / Retry-After |
| `GET /api/v2/optimization-jobs/{id}` | 查询执行状态及结果引用；已受理算法失败仍以 HTTP 200 返回 FAILED 作业 |
| `GET /api/v2/optimization-jobs/{id}/input` | 读取归档的类型规范化输入，用于复现与审计 |
| `POST /api/v2/optimization-jobs/{id}/cancellations` | 请求取消；不需要请求正文，重复取消返回当前真实状态 |
| `GET /api/v2/optimization-results/{id}` | 读取不可变已验证结果；id 与 jobId 相同，未形成结果返回 409 |

提交必须带 `Idempotency-Key`（8–128 个字母、数字、`. _ : -`）。同键同规范化输入返回相同作业，包括已经失败或取消的作业；同键不同输入返回 409。字段顺序和 JSON 空白不影响比对，需求数组顺序、类型、调用方请求编号和选项仍属于输入内容。`clientRequestId` 用于调用方追溯，不代替幂等键。

输入哈希为类型规范化请求的 SHA-256；结果记录 `jobId`、`inputHash`、请求/实际引擎、引擎版本、降级原因及运行耗时。取消/失败作业需要重新计算时，使用新的幂等键。当前幂等范围为整套单实例服务，没有租户隔离；归档不自动过期，也不在达到限额时静默淘汰旧结果。

快速调用（只创建计算作业）：

```sh
curl -fsS http://localhost:8080/api-v2/example-request.json -o /tmp/cutdemo-job-input.json
curl -i -H 'Content-Type: application/json' -H 'Idempotency-Key: integration-example-001' \
  --data-binary @/tmp/cutdemo-job-input.json http://localhost:8080/api/v2/optimization-jobs
# 读取响应 Location 查询作业，再根据 resultRef 读取结果。
```

## 3. 执行、解和履约分别表达

作业：`QUEUED → RUNNING → SUCCEEDED / FAILED`，取消和超时经过 `CANCEL_REQUESTED → CANCELLED / TIMED_OUT`。未开始的排队作业可以直接取消。只返回可观测阶段，不展示伪造百分比。

- `SUCCEEDED` 表示求解与独立校验完成，可能只找到部分排料或没有找到解。
- `layout.status` 返回 `FEASIBLE` 或 `NO_SOLUTION_FOUND`。启发式未找到解不能标为 INFEASIBLE 或 OPTIMAL。
- `fulfillmentStatus` 为 COMPLETE / PARTIAL / NONE；`requireComplete=true` 时，部分排料的 `meetsRequirement=false`。
- `validationStatus=PASSED` 仅出现在已通过独立几何/数量校验的结果。引擎错误及非法候选布局为 FAILED，不发布其几何。
- `terminationReason` 为 COMPLETED / CANCELLED / TIME_LIMIT。取消或超时退出时若仍有已验证结果可保留，不能据此将作业状态改成正常完成。
- 当前明确提供的面积指标是 `processingAreaUtilization`：裁片净面积 ÷ 提交加工区面积 × 100，附 numerator、denominator、basis、version。它不是实际用料利用率，也不是良品报工；实际用料指标仍由执行/报工业务决定。

运行取消通过线程中断发出停止请求；无法及时响应的计算保持 STOPPING，直到计算实际退出才释放并发名额。timeLimitSeconds 从 worker 开始执行计时（排队时间不计），默认支持 1–60 秒；这是协作停止预算，不是保证进程在某一毫秒被硬终止，也不承诺 CPU/内存隔离。

内置 Java 横切、直刀、异形搜索及刀序循环已加入中断检查，独立结果校验也能停止。检查不清除中断标志；中断时尚未完成独立校验的候选不会发布为可行结果。第三方引擎仍须分别验证停止能力，不能由内置引擎的测试推断全部插件可及时停止。

## 4. 持久化和恢复

- 每个作业一个 JSON 文档，含输入、幂等键、状态及最终结果。临时文件写入并 force 后通过原子 rename 替换；不支持原子替换的文件系统会报错，不退化为半写覆盖。
- 服务全生命周期独占作业目录的 OS 文件锁，第二个实例不能使用同一目录。启动发现破损文件会失败并保留文件，不自动初始化空库。
- 所有结果先持久化再对查询可见。磁盘写入失败不会返回未提交的成功结果；若失败状态也写不下，当前进程保留失败状态、停止新受理并写服务日志；重启后按磁盘中的未完成状态恢复。
- 服务重启时，已归档的终态结果继续可读；未完成作业标为 FAILED / PROCESS_RESTARTED。这样已受理请求可追溯，避免无意重复计算；本期不自动续算、不实现分布式抢占。
- 正常关闭请求取消排队和运行任务；计算退出后释放目录锁。被强制终止的未完成请求按上述重启规则处理。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `cutdemo.jobs.path` | `${cutdemo.state.path}.jobs`，未配置库存路径时为 `data/cutdemo-state.json.jobs` | 独立计算目录；不复用库存快照 |
| `cutdemo.jobs.workers` | 2 | 1–16 个计算线程 |
| `cutdemo.jobs.queue-capacity` | 16 | 1–1000 个等待位置 |
| `cutdemo.jobs.max-stored` | 1000 | 作业归档数上限；保留旧幂等记录，达到上限需运维扩容或另行设计归档迁移 |

请求正文上限 262144 字节；既有算法上限为 10000 件，轮廓排料 200 件、展开 10000 顶点。上述是受控默认限额，不是性能 SLA。即使库存使用 MySQL，本阶段计算作业仍使用本地独占目录；不能称为数据库作业服务或多实例高可用服务。

错误格式统一为 `code / message / fieldErrors / traceId / retryable / details`。当前聚合校验使用 message，fieldErrors 为空数组，不伪造字段定位。错误包括 400 INVALID_INPUT、404 NOT_FOUND、409 IDEMPOTENCY_CONFLICT / RESULT_NOT_AVAILABLE、413 PAYLOAD_TOO_LARGE、422 UNSUPPORTED_CONSTRAINT、429 QUOTA_EXCEEDED、503 ENGINE_UNAVAILABLE / SERVICE_UNAVAILABLE。

身份认证、租户、配额分账、持久化调用审计、WMS 及 MCP 权限还未实现；当前适用范围为本地/已有受控宿主调用，不能把 clientRequestId 当作已认证身份。

## 5. 验证入口与下一阶段

`OptimizationServiceTests` 验证持久化、重启、同键并发、取消竞争、超时退出、失败回滚、存储锁、归档限额及严格降级；`OptimizationApiTests` 用真实 HTTP 验证标准状态码、大小限制、输入/结果读取及库存零副作用。既有内核、v1、业务及浏览器回归同时保留。

独立契约验收：在临时 Python venv 安装 `jsonschema` 与 `openapi-spec-validator`，对空库存测试服务执行 `BASE_URL=http://localhost:18080 <venv>/bin/python src/test/integration/optimization-contracts.py`。脚本校验公开文档、示例和实际 HTTP 响应的契约一致性，并核对计算没有产生业务库存；禁止指向用户使用的 8080 服务。

03b 继续数据库作业/尝试模型、租约与 fencing token、多实例调度、可验证的引擎协作取消和资源限制；之后再接入一维、服务端齐套缩长编排和 UI 作业进度。当前页面仍沿用原接口，不将新 API 存在等同于页面完成迁移。
